# Collector Recommendations by Product and Platform

Last reviewed: **11 October 2026**.

Use this guide to choose a collector when a system cannot run THOR directly or when selected files should be analysed on a central Thunderstorm server. For a full local scan on a supported endpoint, prefer THOR; a file collector does not reproduce all endpoint-scanning capabilities.

Common enterprise operating systems and infrastructure appear first, followed by edge appliances and specialist platforms. Ordering is approximately by deployment prevalence, with related products kept together; it is an editorial navigation order, not a measured market-share or exploitation ranking.

Recommendations are inferred from vendor-documented execution environments and our collector requirements. **Unless an exact test record is linked, the combination is a candidate, not product-tested support.** A shell or matching CPU does not establish permission, kernel compatibility, required utilities, or visibility of all host files. Use the vendor-approved procedure and verify the actual firmware before collection.

## Direct THOR Scanning and ARM64

Nextron's [Management Center 4.1.1 announcement](https://management-center-manual.nextron-systems.com/en/latest/changelog/log1.html#management-center-4-1-1) identifies **Windows ARM64 and Linux ARM64** support with the upcoming **THOR 11** release. Once the released THOR package supports the target OS and local scanning is permitted, a collector is no longer needed solely to work around the ARM64 architecture.

This does not establish support for 32-bit ARM, every legacy Linux kernel, old Windows versions, or appliance firmware. Collectors remain useful for those gaps and for central file-analysis workflows. Check the [requirements of the actual THOR release](https://thor-manual.nextron-systems.com/en/latest/usage/requirements.html) before replacing a collector workflow.

### Nutanix execution restrictions

An existing Linux shell does not establish permission to run a collector on AHV or a CVM. A [2020 Nutanix employee advisory](https://next.nutanix.com/installation-configuration-23/antivirus-on-nutanix-ahv-hosts-and-on-cvms-37041) specifically discourages third-party software execution on both. The [current third-party support policy](https://www.nutanix.com/en_gb/support-services/support-policies-and-faqs?show=accordion-0) also describes possible support limitations. Confirm the permitted collection procedure with Nutanix; without that confirmation, prefer approved exports and upload from a separate system. A standalone binary requiring no package installation does not by itself remove this restriction.

### Compatibility Boundaries

The [current release workflow](../.github/workflows/release.yml) uses Go 1.10.8 for regular targets supported by that compiler and stable Go for additional targets; the NetScaler build is separate. This describes current build selection, not the compiler of every historical archive. Check the selected package's compiler and the [corresponding Go requirements](https://go.dev/wiki/MinimumRequirements).

- **Older operating systems:** Go 1.10's historical Linux minimum is **2.6.23**, with additional architecture requirements. It requires **FreeBSD 10.3+**, **NetBSD 8 for x86**, and **OpenBSD 6.0**. Go 1.10 was the last release supporting Windows XP/Vista and OS X 10.8/10.9. These baselines do not transfer to stable-Go packages or guarantee compatibility with every newer OS. See the [Go 1.10 installation requirements](https://github.com/golang/go/blob/go1.10.8/doc/install.html) and [port notes](https://go.dev/doc/go1.10#ports).
- **ARM:** `arm64` means AArch64; `arm` is a separate 32-bit target. The Go 1.10.8 cross-build from an amd64 host defaults to `GOARM=5` for the listed Linux/BSD targets; check the actual kernel, CPU and ABI as well. That flag alone does not prove compatibility with a Linux 2.6 kernel. See the [compiler's default selection](https://github.com/golang/go/blob/go1.10.8/src/cmd/dist/util.go).
- **MIPS and PowerPC:** `mips`/`mips64` and `ppc64` are big-endian; the `le` variants are little-endian. The workflow does not override `GOMIPS`, so Go 1.10's 32-bit MIPS builds use the hard-float default. A matching filename is insufficient for a router without the required floating-point hardware. Go 1.9+ PowerPC ports require POWER8. See the [Go 1.10 MIPS settings](https://go.dev/doc/go1.10#ports) and [CPU requirements](https://go.dev/wiki/MinimumRequirements).
- **Solaris and AIX:** The Solaris port baseline is Solaris 11 / SunOS 5.11 on amd64; it does not cover SPARC. The AIX port was introduced for AIX 7.2+ on POWER8. Validate the exact release and processor against the selected compiler; use existing script fallbacks only when their dependencies are available. See the [Solaris matrix](https://go.dev/wiki/Solaris) and [AIX port requirements](https://go.dev/doc/go1.12#aix).

The binaries require no installed Go runtime. They still depend on compatible system calls, CPU features and access to the intended files. For systems below a binary's runtime floor, use an existing script only when its interpreter, utilities and HTTP transport meet the requirements above.

## Why Include These Edge Platforms?

The additions combine useful execution environments with incident-response relevance. Vendor and first-hand reports document [Fortinet persistent access](https://www.fortinet.com/uk/blog/psirt-blogs/analysis-of-threat-actor-activity), [PAN-OS exploitation](https://security.paloaltonetworks.com/CVE-2024-3400), [Sophos firewall campaigns including older appliances](https://www.sophos.com/en-us/blog/pacific-rim-timeline), [SonicWall SMA100 exploitation](https://cloud.google.com/blog/topics/threat-intelligence/sonicwall-secure-mobile-access-exploitation-overstep-backdoor), and [QNAP DEADBOLT attacks](https://www.qnap.com/en-us/security-advisory/qsa-22-02). These establish investigation relevance, not collector compatibility or relative market share.

Synology's [SynoLocker advisory](https://www.synology.com/en-af/security/advisory/SynoLocker) is historical evidence, not a claim of a current campaign. OpenWrt and pfSense/OPNsense are included as accessible edge platforms; this guide does not label them frequent victims merely because other routers and firewalls are targeted.

## External Collection and File Visibility

External collection means exporting or copying approved files using the product's documented mechanisms, then running a collector on the receiving system with an explicit input directory. It is a workflow, not a built-in SSH/API acquisition mode. Preserve the original files and source identity separately and verify how the backend represents exported filenames and source identifiers.

The collector can upload only files visible and readable in its execution environment and admitted by its filters. An AHV host is not its CVM or its guest VMs; an ESXi host is not vCenter; a container's filesystem is not automatically its node's filesystem. Review size, age, extension and filesystem exclusions for the intended inputs, especially large exports or core files. These recommendations do not establish that Thunderstorm analyzes every possible export format.

## Test Evidence

The [script acceptance report](SCRIPT_COLLECTOR_ACCEPTANCE_2026-10-08.md) records exact revisions, runtime versions, hashes and outstanding checks. Its successful real-THOR runs do not certify all products listed above. The [NetScaler/FreeBSD record](../go/README.md#compatibility-evidence-as-of-2026-10-08) separately identifies the tested legacy artifact and VM environments.

For a new product test, record product/firmware, OS and architecture, collector revision or asset hash, runtime, execution context and visible paths, HTTP/HTTPS mode, dry-run outcome and server-side receipt/results. Link that record here before changing a recommendation from an untested candidate to a product-tested combination. Runtime availability, successful startup and successful end-to-end collection are different evidence levels.
